# LeKiwi の掃き掃除タスク（Sweep）

LeKiwi（台車 + SO101 アーム）に手箒を持たせ、床のゴミを目標の領域へ掃き集める動作を学習させる。このページは、実装の前提（確認した事実、仮定、コスト）と進み具合をまとめる。作業を中断したら、このページから再開する。

## 確定事項（2026-10-29）

| 項目 | 内容 |
|---|---|
| 対象 | まずは床だけ。段差の上のゴミは P7 で扱う。ヒューマノイド向けの抽象化はしない |
| 手箒 | 全長 30cm（柄 18cm、ブラシ部 12cm）、ブラシの幅 20cm、100g。グリッパのリンクに固定し、グリッパは閉じた一定の角度にする |
| ゴミ | 2〜3cm、5〜10g を 10 個（`debris_0` 〜 `debris_9`） |
| 目標領域 | 床の上の 30cm 角の色付きの正方形（見た目だけで、衝突形状なし）。位置はランダム |
| 成功条件 | 10 個中 8 個以上が目標領域に入る |
| カメラ | front と wrist の 2 台、320×240 |
| アームの重力 | 上流と同じく切ったまま（後述の「実機との差」） |
| 自動生成 | 計画器の合格ラインは、30 ラウンドで成功率 70% 以上。最初のデモは 50 エピソード |
| ポリシー | P6 で決める |

## 全体の流れ

```
計画器（特権情報を使う古典的な手法）── sweep_eval --record ──> HDF5 + .sim.env（元データ）
                                                                   │ make convert（train イメージ、contract.py）
                                                                   v
                                                             LeRobot 形式 ──> 学習（P6）
学習したポリシー ── sweep_eval（remote）──> 成功率（計画器と同じ方法で測る）
```

- 計画器は、sim の真値（ゴミの位置、目標領域の位置、台車の姿勢、関節の角度）を読んで動く。成功と失敗の判定も真値で行い、成功したエピソードだけを残す。
- 学習するポリシーが見るのは、カメラ画像と自分の関節・台車の状態だけ。

## データの約束事（`tools/leisaac_ext/contract.py`）

sim、変換、学習、推論のすべてが、このファイルの定義に従う。isaaclab も lerobot も import しないので、sim と train の両方で読み込める。

| 項目 | 内容 | 根拠 |
|---|---|---|
| state と action のキー | `arm_shoulder_pan.pos` 〜 `arm_gripper.pos`、`x.vel`、`y.vel`、`theta.vel` | 実機の LeRobot LeKiwi（lerobot 0.4.2 の `robots/lekiwi/lekiwi.py`） |
| アームの単位 | モータの正規化値（-100〜100、グリッパは 0〜100） | 実機の既定（`use_degrees=False`）。sim の rad からの変換は上流の `convert_leisaac_action_to_lerobot` と同じ式 |
| 台車の単位 | ロボット基準。`x.vel` は前進（m/s）、`y.vel` は左（m/s）、`theta.vel` は反時計回り（**deg/s**） | 実機の `_body_to_wheel_raw`。上流の sim の変換（`user_vel_*`）は theta を rad/s のまま出すので、ここで deg/s にする |
| sim の action | `lekiwi-leader` の構成（9 次元）: アームの関節位置（rad）5、グリッパ（rad）1、台車の速度 3（x と y はワールド座標系、θ は rad/s） | `devices/action_process.py` |
| sim の観測の関節の並び | `base_x`、`base_y`、`base_theta`、アーム 6（`SIM_JOINT_NAMES`）。action とは並びが違う | PhysX が決める articulation の並び。2026-10-29 に sim で確認（箒の有無で変わらない） |
| フレームレート | 学習データは 30fps。sim は 60Hz のままで、ポリシーと計画器は同じ action を 2 step 続ける。変換では 1 step おきに取り出す | 記録は 60Hz で、画像の半分は重複している |
| 台車の action のラベル | env に渡した値を、その step の観測時の向きで変換する | 上流の `build_lerobot_frame` は 1 step 後の観測を使うので、ラベルが 1 フレーム遅れる |
| カメラ | `front`、`wrist`。320×240 の RGB | 確定事項 |
| 指示文 | 固定（`INSTRUCTION`） | — |
| グリッパ | 一定の角度 `GRIPPER_HOLD_RAD = 0`（上流の初期値と同じ） | 箒を固定するので、グリッパの開閉は使わない。関節が 0 のとき、厚さ 12mm の柄がどちらの指にも触れない |

- 変換は、上流の変換関数と誤差 1e-13 以下で一致することを確認した（2026-10-29、sim のイメージの中で、乱数の入力 100 個）。env の中の値との一致は、P2 のテストで確かめる。
- 上流の `build_lerobot_frame` は、state のアームを `joint_pos[:-3]` で取り出しているが、実際の並びでは先頭が台車なので、台車の 3 関節がアームの値に混ざる（上流の不具合と考えられる）。自前の変換器は関節名から添字を求めるので、この影響を受けない。

## 手箒（`tools/leisaac_ext/broom.py`）

- 剛体 `broom` を lekiwi.usd に足し、gripper のリンクと固定ジョイントでつなぐ（車輪と同じ作り）。関節の並びは変わらない。
- 寸法: 柄は 12×25×180mm で 30g、穂は 20×200×120mm で 70g（直方体 2 つ）。質量、重心、慣性は、この 2 つから計算して明示する。
- 握り方: 指先はグリッパの座標系の -z 方向に伸び、x 方向に挟む。指の間（z = -0.055 から）で柄を握り、穂の幅は y 方向。
- 重力: アームと同じく切る。タスクのイベント `disable_arm_gravity` の対象に `broom` を足す（P2）。
- 接触モデル: PhysX の既定（剛体の接触）。穂の摩擦は静止 0.5、動 0.4。
  - アームのゲインが低い（stiffness 12.8）ので、アーム自体が柔らかいばねとして働く。柔らかい接触や、穂先を浮かせる工夫は使わない。
  - 確認（2026-10-29、床だけのシーン、CPU 物理）:
    - 静止 10 秒: アームの関節速度は最大 1.1e-3 rad/s、穂先の移動は 0.001mm。
    - 穂を床に押し付けたまま 5 秒保持（wrist_flex は目標より 0.2 rad 手前で止まる）: めり込みは 0.1mm 以下。穂先がゆっくり約 1mm 滑るだけで、振動はない。
  - 関節が 0 の姿勢では、穂の面は床とほぼ平行で、穂先はロボットの前方約 65cm、高さ約 22cm にある。穂を床に当てるには、wrist_flex を + 方向に約 0.65 rad 倒す。ただし、そのままでは穂の角が先に床に当たるので、wrist_roll で合わせる（P3 の計画器で扱う）。

## 床のタスク（`tools/leisaac_ext/sweep_floor.py`）

タスク名は `LeIsaac-LeKiwi-Sweep-Floor-v0`。action は `lekiwi-leader` の構成（9 次元）で使う。部品（配置、ランダム化、指標、成功の判定）は `tools/leisaac_ext/sweep_mdp.py` にある。

| 要素 | 内容 |
|---|---|
| 床 | 8m 四方の直方体。外部のアセットを使わない（Nucleus の GroundPlane は、実行時にネットから取得するため）。摩擦は静止 0.6、動 0.5 |
| 照明 | 上流のテンプレートの DomeLight。強さだけ 3000 から 1000 に下げる（床だけのシーンでは白飛びする） |
| ロボット | 箒付きの LeKiwi。env の原点に置き、前は +y。高さは 0.035m（上流の CleanupTrash と同じ。z=0 では車輪が床にめり込み、台車が動かない） |
| ゴミ | `debris_0` 〜 `debris_9`。立方体で、大きさ 2〜3cm と質量 5〜10g を番号ごとに振り分ける。色も番号ごとに変える |
| 目標領域 | `target`。30cm 角、厚さ 2mm の青い板。衝突と重力のない剛体にして、位置を状態として記録・復元できるようにする（kinematic にすると、上流のリセットが速度を書き込み、PhysX がエラーを出す） |
| 配置 | リセットのたびに `reset_layout` が決める。ゴミのまとまりの中心は x が -0.4〜0.4m、y が 0.9〜1.5m。そのまわりの 4×3 の格子（8cm 間隔、全体をランダムに回す）から 10 升を選び、±1.5cm ずらして置く。目標領域の中心は x が -0.9〜0.9m、y が 0.5〜2.2m の範囲で、まとまりの中心から 0.45〜0.7m 離す。さらに、ゴミすべてと目標領域の四隅が front カメラから見て ±24° 以内に入る配置だけを選ぶ（最初の画像に両方が写る）。候補 256 個のうち約 8% が条件を満たす。目標領域の方向（ゴミから見た向き）は、奥側が多いが、横や手前側にもなる |
| 成功 | ゴミの中心が目標領域の中（xy）にあり、高さが 5cm 未満のものが 8 個以上で、終了条件 `success` が成り立つ。上流の評価スクリプトは、これを成功として数える。指標（ゴミごとに中に入っているか）は `debris_in_target` |
| カメラ | front と wrist を 320×240 にする。取り付け位置とレンズは上流のまま。front は約 10° 下向きで、床から約 6cm の高さにある。水平の画角は約 54°（上流のコメントには 75° とあるが、`focal_length` 36.5 と `horizontal_aperture` 36.83 から計算すると 53.5°） |
| リセット後の描画 | `rerender_on_reset=True`。既定の False では、`reset` が返す画像がリセット前の場面のままになり、記録の最初のフレームが前のエピソードの画像になる |
| 把持力の自動調整 | 切る（`dynamic_reset_gripper_effort_limit=False`）。箒は固定なので不要 |

### ランダム化

配置（上の表）は常に有効。追加の項目は `set_randomization` で選ぶ（`sweep_check.py --randomize all` で全部）。

| 項目 | 内容 | 既定 |
|---|---|---|
| `debris_color` | ゴミの色（青を避ける） | 有効 |
| `light` | 照明の強さを 0.6〜1.4 倍、色を各成分 ±10% | 有効 |
| `camera` | front と wrist の取り付け位置を ±5mm、向きを ±0.03rad ずらす | 有効 |
| `debris_mass` | ゴミの質量を 5〜10g | 無効 |
| `debris_friction` | ゴミの摩擦を静止 0.3〜0.8（床の摩擦の違いの代わり。PhysX は 2 つの物体の摩擦の平均を使う） | 無効 |

- コストは、どの項目もほぼない。全部有効にしても、リセットは 1 回 0.01 秒から 0.02 秒、速さは 79 steps/s から 77 steps/s で、VRAM は変わらない（2026-10-30）。
- 質量と摩擦は、記録される状態（初期状態）に含まれない。有効にすると、記録したエピソードを replay で再現できなくなる（P4 の完了条件）ので、既定では使わない。
- ゴミの大きさは、リセットのたびには変えられない（形状は起動時に決まる）。代わりに、番号ごとに大きさを変えてある。
- 上流の部品を使わなかったもの:
  - `randomize_visual_color`（replicator を使う）: 項目ごとの乱数が同じ系列になり、ゴミがすべて同じ色になった。PreviewSurface の色を直接書き換える `randomize_color` を使う。
  - `randomize_camera_uniform`: 現在の姿勢に乱数を足すので、リセットのたびにずれが累積する。設定値を基準にする `randomize_camera_offset` を使う。

### 確認（`make sweep-check`、`make check` の 5 番目）

`tools/sweep_check.py` が次を確かめる（2026-10-30、CPU 物理、ヘッドレス）。

- 関節の並びが `SIM_JOINT_NAMES` と一致する。
- front と wrist の画像が 240×320×3。画像は `data/sweep/check/` に保存する。
- 決めた action（アームを振り、台車を回しながら動かす）を 300 step 流し、`to_lerobot` が上流の変換と一致する。誤差は、アームが 1.3e-5、台車が 1e-6 以下。
  - 上流の `user_vel_*` は、絶対値が 1e-4 未満の値を 0 に丸める。contract は丸めないので、比較のときだけ同じ丸めを入れる。
  - 上流の state のアーム（`joint_pos[:-3]`）との差は、最大 135（モータの値）になる（台車の関節が混ざるため）。
- 台車が指令どおりに動く。並進のずれは 1.5e-3 m/s 以下。回転は、最大 0.022 rad/s（指令 0.4 rad/s の約 5%）遅れ、5 秒間の平均では指令の 98% になる。学習のラベルには指令値を使うので、contract には影響しない。
- リセットを 5 回繰り返し（`--resets`）、ゴミが重ならない（間隔 3.5cm 超。実測は 4.5cm 以上）、目標領域に入っていない、ゴミと目標領域が front の画角に入る（実際のカメラの位置から見た方位が半画角 26.8° 未満。実測は最大 23.6°）、0.5 秒後も動いていない、リセット直後の画像が新しい場面を写している。
- 目標領域にゴミを 7 個置くと成功にならず、8 個で成功になる。
- コスト: VRAM のピークは 2.9〜3.3GB、Kit のプロセスの RAM のピークは 5.6GB、速さは約 79 steps/s（実時間の 1.3 倍）。Kit の起動から終了まで約 30 秒（シェーダのキャッシュがある場合）。
- 見え方（320×240）: front では、1〜2m 先のゴミが 1 個 5〜10 ピクセル、目標領域は斜めから見た細い青い帯として写る（カメラが低いため）。近づけば大きくなる。穂が画面の左上に写り込む。wrist は、柄と指が視野の大半を占める。

## 実機との差（既知）

| 項目 | sim | 実機 | 対応 |
|---|---|---|---|
| アームの重力 | 切っている（上流のイベント `disable_arm_gravity`） | ある | 実機に移す段階で、重力を入れて関節のゲインを調整する |
| 物理演算 | CPU（全タスク共通の設定。docs/decisions.md） | — | 記録と評価は同じ設定で行う |
| アームの角度の対応 | USD の関節の可動域を、モータの -100〜100 に線形に対応させる（上流の方式） | キャリブレーションで決まる | 実機に移す段階で確認する |
| wrist カメラ | 320×240（横長） | 480×640（縦長。`ROTATE_90`） | 実機に移す段階で、向きと縮小のしかたを合わせる |
| 台車 | 仮想の関節を速度で動かす（車輪は回らない）。回転は指令より数 % 遅れる | 3 輪のオムニホイール | 速度と加速度の上限を、実機に近い値に抑える |
| 照明と床 | 一様な DomeLight と、単色の床 | 部屋による | 照明と色のランダム化で幅を持たせる。実機に移す段階で、実際の床で確かめる |
