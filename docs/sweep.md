# LeKiwi の掃き掃除タスク（Sweep）

LeKiwi（台車 + SO101 アーム）に手箒を持たせ、床のゴミを目標の領域へ掃き集める動作を学習させる。このページは、実装の前提（確認した事実、仮定、コスト）と進み具合をまとめる。作業を中断したら、このページから再開する。

## 確定事項（2026-10-29）

| 項目 | 内容 |
|---|---|
| 対象 | まずは床だけ。段差の上のゴミは P7 で扱う。ヒューマノイド向けの抽象化はしない |
| 手箒 | 全長 30cm（柄 18cm、ブラシ部 12cm）、ブラシの幅 20cm、100g。グリッパのリンクに固定し、グリッパは閉じた一定の角度にする |
| ゴミ | 2〜3cm、5〜10g を 10 個（`debris_0` 〜 `debris_9`） |
| 目標領域 | 床の上の 30cm 角の色付きの正方形（見た目だけで、衝突形状なし）。位置はランダム |
| 成功条件 | 10 個中 8 個以上が目標領域に入る |
| カメラ | front と wrist の 2 台、320×240 |
| アームの重力 | 上流と同じく切ったまま（後述の「実機との差」） |
| 自動生成 | 計画器の合格ラインは、30 ラウンドで成功率 70% 以上。最初のデモは 50 エピソード |
| ポリシー | P6 で決める |

## 全体の流れ

```
計画器（特権情報を使う古典的な手法）── sweep_eval --record ──> HDF5 + .sim.env（元データ）
                                                                   │ make convert（train イメージ、contract.py）
                                                                   v
                                                             LeRobot 形式 ──> 学習（P6）
学習したポリシー ── sweep_eval（remote）──> 成功率（計画器と同じ方法で測る）
```

- 計画器は、sim の真値（ゴミの位置、目標領域の位置、台車の姿勢、関節の角度）を読んで動く。成功と失敗の判定も真値で行い、成功したエピソードだけを残す。
- 学習するポリシーが見るのは、カメラ画像と自分の関節・台車の状態だけ。

## データの約束事（`tools/leisaac_ext/contract.py`）

sim、変換、学習、推論のすべてが、このファイルの定義に従う。isaaclab も lerobot も import しないので、sim と train の両方で読み込める。

| 項目 | 内容 | 根拠 |
|---|---|---|
| state と action のキー | `arm_shoulder_pan.pos` 〜 `arm_gripper.pos`、`x.vel`、`y.vel`、`theta.vel` | 実機の LeRobot LeKiwi（lerobot 0.4.2 の `robots/lekiwi/lekiwi.py`） |
| アームの単位 | モータの正規化値（-100〜100、グリッパは 0〜100） | 実機の既定（`use_degrees=False`）。sim の rad からの変換は上流の `convert_leisaac_action_to_lerobot` と同じ式 |
| 台車の単位 | ロボット基準。`x.vel` は前進（m/s）、`y.vel` は左（m/s）、`theta.vel` は反時計回り（**deg/s**） | 実機の `_body_to_wheel_raw`。上流の sim の変換（`user_vel_*`）は theta を rad/s のまま出すので、ここで deg/s にする |
| sim の action | `lekiwi-leader` の構成（9 次元）: アームの関節位置（rad）5、グリッパ（rad）1、台車の速度 3（x と y はワールド座標系、θ は rad/s） | `devices/action_process.py` |
| sim の観測の関節の並び | `base_x`、`base_y`、`base_theta`、アーム 6（`SIM_JOINT_NAMES`）。action とは並びが違う | PhysX が決める articulation の並び。2026-10-29 に sim で確認（箒の有無で変わらない） |
| フレームレート | 学習データは 30fps。sim は 60Hz のままで、ポリシーと計画器は同じ action を 2 step 続ける。変換では 1 step おきに取り出す | 記録は 60Hz で、画像の半分は重複している |
| 台車の action のラベル | env に渡した値を、その step の観測時の向きで変換する | 上流の `build_lerobot_frame` は 1 step 後の観測を使うので、ラベルが 1 フレーム遅れる |
| カメラ | `front`、`wrist`。320×240 の RGB | 確定事項 |
| 指示文 | 固定（`INSTRUCTION`） | — |
| グリッパ | 一定の角度 `GRIPPER_HOLD_RAD = 0`（上流の初期値と同じ） | 箒を固定するので、グリッパの開閉は使わない。関節が 0 のとき、厚さ 12mm の柄がどちらの指にも触れない |

- 変換は、上流の変換関数と誤差 1e-13 以下で一致することを確認した（2026-10-29、sim のイメージの中で、乱数の入力 100 個）。env の中の値との一致は、P2 のテストで確かめる。
- 上流の `build_lerobot_frame` は、state のアームを `joint_pos[:-3]` で取り出しているが、実際の並びでは先頭が台車なので、台車の 3 関節がアームの値に混ざる（上流の不具合と考えられる）。自前の変換器は関節名から添字を求めるので、この影響を受けない。

## 手箒（`tools/leisaac_ext/broom.py`）

- 剛体 `broom` を lekiwi.usd に足し、gripper のリンクと固定ジョイントでつなぐ（車輪と同じ作り）。関節の並びは変わらない。
- 寸法: 柄は 12×25×180mm で 30g、穂は 20×200×120mm で 70g（直方体 2 つ）。質量、重心、慣性は、この 2 つから計算して明示する。
- 握り方: 指先はグリッパの座標系の -z 方向に伸び、x 方向に挟む。指の間（z = -0.055 から）で柄を握り、穂の幅は y 方向。
- 重力: アームと同じく切る。タスクのイベント `disable_arm_gravity` の対象に `broom` を足す（P2）。
- 接触モデル: PhysX の既定（剛体の接触）。穂の摩擦は静止 0.5、動 0.4。
  - アームのゲインが低い（stiffness 12.8）ので、アーム自体が柔らかいばねとして働く。柔らかい接触や、穂先を浮かせる工夫は使わない。
  - 確認（2026-10-29、床だけのシーン、CPU 物理）:
    - 静止 10 秒: アームの関節速度は最大 1.1e-3 rad/s、穂先の移動は 0.001mm。
    - 穂を床に押し付けたまま 5 秒保持（wrist_flex は目標より 0.2 rad 手前で止まる）: めり込みは 0.1mm 以下。穂先がゆっくり約 1mm 滑るだけで、振動はない。
  - 関節が 0 の姿勢では、穂の面は床とほぼ平行で、穂先はロボットの前方約 65cm、高さ約 22cm にある。穂を床に当てるには、wrist_flex を + 方向に約 0.65 rad 倒す。ただし、そのままでは穂の角が先に床に当たるので、wrist_roll で合わせる（P3 の計画器で扱う）。

## 床のタスク（`tools/leisaac_ext/sweep_floor.py`）

タスク名は `LeIsaac-LeKiwi-Sweep-Floor-v0`。action は `lekiwi-leader` の構成（9 次元）で使う。部品（配置、ランダム化、指標、成功の判定）は `tools/leisaac_ext/sweep_mdp.py` にある。

| 要素 | 内容 |
|---|---|
| 床 | 8m 四方の直方体。外部のアセットを使わない（Nucleus の GroundPlane は、実行時にネットから取得するため）。摩擦は静止 0.6、動 0.5 |
| 照明 | 上流のテンプレートの DomeLight。強さだけ 3000 から 1000 に下げる（床だけのシーンでは白飛びする） |
| ロボット | 箒付きの LeKiwi。env の原点に置き、前は +y。高さは 0.035m（上流の CleanupTrash と同じ。z=0 では車輪が床にめり込み、台車が動かない） |
| ゴミ | `debris_0` 〜 `debris_9`。立方体で、大きさ 2〜3cm と質量 5〜10g を番号ごとに振り分ける。色も番号ごとに変える |
| 目標領域 | `target`。30cm 角、厚さ 2mm の青い板。衝突と重力のない剛体にして、位置を状態として記録・復元できるようにする（kinematic にすると、上流のリセットが速度を書き込み、PhysX がエラーを出す） |
| 配置 | リセットのたびに `reset_layout` が決める。ゴミのまとまりの中心は x が -0.4〜0.4m、y が 0.9〜1.5m。そのまわりの 4×3 の格子（8cm 間隔、全体をランダムに回す）から 10 升を選び、±1.5cm ずらして置く。目標領域の中心は x が -0.9〜0.9m、y が 0.5〜2.2m の範囲で、まとまりの中心から 0.45〜0.7m 離す。さらに、ゴミすべてと目標領域の四隅が front カメラから見て ±24° 以内に入る配置だけを選ぶ（最初の画像に両方が写る）。候補 256 個のうち約 8% が条件を満たす。目標領域の方向（ゴミから見た向き）は、奥側が多いが、横や手前側にもなる |
| 成功 | ゴミの中心が目標領域の中（xy）にあり、高さが 5cm 未満のものが 8 個以上で、終了条件 `success` が成り立つ。上流の評価スクリプトは、これを成功として数える。指標（ゴミごとに中に入っているか）は `debris_in_target` |
| カメラ | front と wrist を 320×240 にする。取り付け位置とレンズは上流のまま。front は水平より約 10° **上**向きで（取り付けの回転は opengl の向きで x 軸まわり 100°。2026-11-01 まで「下向き」と誤記していた）、床から約 6cm の高さにある。床は画面の下 1/4 ほどにしか写らない。水平の画角は約 54°（上流のコメントには 75° とあるが、`focal_length` 36.5 と `horizontal_aperture` 36.83 から計算すると 53.5°）。wrist は握った箒の柄しか写らない。見直しは下の「カメラの見直し」 |
| リセット後の描画 | `rerender_on_reset=True`。既定の False では、`reset` が返す画像がリセット前の場面のままになり、記録の最初のフレームが前のエピソードの画像になる |
| 把持力の自動調整 | 切る（`dynamic_reset_gripper_effort_limit=False`）。箒は固定なので不要 |

### カメラの見直し（`make sweep-camera-probe`、2026-11-01）

実験 5〜7（sweep_experiments.md）で、失敗の主な原因は「ポリシーにゴミが見えていない」ことだった。カメラの取り付けを見直す。実機のカメラは、sim で決めた取り付けに合わせて付け直す前提（ユーザーが了承）。

- `make sweep-camera-probe` は、候補のカメラ（`tools/sweep_camera_probe.py` の `FRONT`、`WRIST`）を追加のセンサとして足した env で、計画器を動かし、同じ場面（移動を始めるとき、移動の 1.5 秒後、押し始めて 0.3 秒後）を全候補で撮って `data/sweep/camera_probe/{front,wrist}.png` に並べる。
- env を作った後でカメラの取り付けの姿勢や焦点距離を書き換えると、次の step の描画から反映される（step せずに描画しても反映されない。関節の状態を直接書き換えたときも同じ）。カメラの向きのランダム化（リセットで書き換え、その後 step する）は効いている。
- 結果（seed 1、2）:

| 候補 | 見え方 |
|---|---|
| front 今（床から 6cm、+10°、f36.5） | 床は画面の下の帯だけ。ゴミは地平線の近くに数ピクセル。押す間は穂が画面の右下を隠す |
| front 6cm、-10°、f24 | 床は広がるが、ゴミは地平線の近くのまま（低すぎる） |
| **front 台車の上 0.2m（床から 0.235m）、-30°、f24** | 移動の間もゴミと目標領域がはっきり写る。押す間は穂先と、その前のゴミと目標領域が同時に写る |
| front 0.2m、-30°、f18 | 同上で広いが、ゴミが小さい。画面の上の端にアームが入る |
| front 0.35m、-40° | アームが画面の大半を隠す |
| wrist 今 | 柄だけ |
| wrist +30°、f24 | 押す間はゴミが近くに大きく写る。移動の間は柄が中央 |
| **wrist +60°、f24** | 移動の間も押す間も、ゴミと目標領域が写る。柄は画面の下の端 |
| wrist -30°、-60° | グリッパと腕しか写らない |

- **採用（2026-11-01、ユーザーが決定）**: front は台車の上 0.2m、30° 下向き、f24。wrist は上流の向きから 45° 回し、f24（30° と 60° の間）。`sweep_floor.py` の `FRONT_POS`、`FRONT_PITCH_DEG`、`WRIST_TILT_DEG`、`FOCAL_LENGTH`。水平の画角は約 75°。
  - 計画器で確認: 3/3 成功、時間も配置も見直し前と同じ（カメラは物理に影響しない）。wrist は、押す間は穂の前のゴミと目標領域が大きく写るが、回り込みの途中（アームは移動の姿勢）ではゴミが画面から外れることがある。front は移動の間もゴミと目標領域を写す。
  - 配置の条件（ゴミと目標領域が front から ±24° 以内）は、見直し前の値のまま（`LAYOUT_MAX_BEARING`）。配置の分布をそろえ、同じシードで同じ配置にするため。`view_fraction` の画角は新しい半画角（約 37.5°）で数える。
  - 実機: front は高さ約 0.2m の支柱、wrist は角度を変えた取り付け具で、この姿勢に合わせる（「実機との差」）。

### ランダム化

配置（上の表）は常に有効。追加の項目は `set_randomization` で選ぶ（`sweep_check.py --randomize all` で全部）。

| 項目 | 内容 | 既定 |
|---|---|---|
| `debris_color` | ゴミの色（青を避ける） | 有効 |
| `light` | 照明の強さを 0.6〜1.4 倍、色を各成分 ±10% | 有効 |
| `camera` | front と wrist の取り付け位置を ±5mm、向きを ±0.03rad ずらす | 有効 |
| `debris_mass` | ゴミの質量を 5〜10g | 無効 |
| `debris_friction` | ゴミの摩擦を静止 0.3〜0.8（床の摩擦の違いの代わり。PhysX は 2 つの物体の摩擦の平均を使う） | 無効 |

- コストは、どの項目もほぼない。全部有効にしても、リセットは 1 回 0.01 秒から 0.02 秒、速さは 79 steps/s から 77 steps/s で、VRAM は変わらない（2026-10-30）。
- 質量と摩擦は、記録される状態（初期状態）に含まれない。有効にすると、記録したエピソードを replay で再現できなくなる（P4 の完了条件）ので、既定では使わない。
- ゴミの大きさは、リセットのたびには変えられない（形状は起動時に決まる）。代わりに、番号ごとに大きさを変えてある。
- 上流の部品を使わなかったもの:
  - `randomize_visual_color`（replicator を使う）: 項目ごとの乱数が同じ系列になり、ゴミがすべて同じ色になった。PreviewSurface の色を直接書き換える `randomize_color` を使う。
  - `randomize_camera_uniform`: 現在の姿勢に乱数を足すので、リセットのたびにずれが累積する。設定値を基準にする `randomize_camera_offset` を使う。
- `debris_color` は、P2 の時点では効いていなかった（2026-10-30 の P3 で修正）。シーンを作った後の `prim_path` は `{ENV_REGEX_NS}` が展開済みで、色を変える prim が見つからず、リセットのたびに `Ill-formed SdfPath` の警告が出ていた。いまは prim が見つからなければ止まる。

### 確認（`make sweep-check`、`make check` の 5 番目）

`tools/sweep_check.py` が次を確かめる（2026-10-30、CPU 物理、ヘッドレス）。

- 関節の並びが `SIM_JOINT_NAMES` と一致する。
- front と wrist の画像が 240×320×3。画像は `data/sweep/check/` に保存する。
- 決めた action（アームを振り、台車を回しながら動かす）を 300 step 流し、`to_lerobot` が上流の変換と一致する。誤差は、アームが 1.3e-5、台車が 1e-6 以下。
  - 上流の `user_vel_*` は、絶対値が 1e-4 未満の値を 0 に丸める。contract は丸めないので、比較のときだけ同じ丸めを入れる。
  - 上流の state のアーム（`joint_pos[:-3]`）との差は、最大 135（モータの値）になる（台車の関節が混ざるため）。
- 台車が指令どおりに動く。並進のずれは 1.5e-3 m/s 以下。回転は、最大 0.022 rad/s（指令 0.4 rad/s の約 5%）遅れ、5 秒間の平均では指令の 98% になる。学習のラベルには指令値を使うので、contract には影響しない。
- リセットを 5 回繰り返し（`--resets`）、ゴミが重ならない（間隔 3.5cm 超。実測は 4.5cm 以上）、目標領域に入っていない、ゴミと目標領域が front の画角に入る（実際のカメラの位置から見た方位が半画角 26.8° 未満。実測は最大 23.6°）、0.5 秒後も動いていない、リセット直後の画像が新しい場面を写している（リセットの前に台車を回して視点を変えておき、リセット前から大きく変わった画素の中で、リセット直後の画像が 0.5 秒後の画像とまだ違う割合が 0.5 未満。古い場面のままなら 1 に近い。2026-11-01 から。それまでは画像全体の平均の差で比べていたが、カメラを見直して床が大半を写すようになり、前後の差が描画の雑音と見分けにくくなった。実測は 0.01〜0.09）。
- 目標領域にゴミを 7 個置くと成功にならず、8 個で成功になる。
- コスト: VRAM のピークは 2.9〜3.3GB、Kit のプロセスの RAM のピークは 5.6GB、速さは約 79 steps/s（実時間の 1.3 倍）。Kit の起動から終了まで約 30 秒（シェーダのキャッシュがある場合）。
- 見え方（320×240）: front では、1〜2m 先のゴミが 1 個 5〜10 ピクセル、目標領域は斜めから見た細い青い帯として写る（カメラが低いため）。近づけば大きくなる。穂が画面の左上に写り込む。wrist は、柄と指が視野の大半を占める。

## 計画器（`tools/leisaac_ext/sweep_planner.py`）

特権情報（sim の真値）を使う古典的な手法。自動生成（P4）のデモを作り、学習したポリシーと比べる基準にもなる。

- **動作**: 穂を床に押し当てたまま台車をまっすぐ前に進め、穂先の前のゴミを目標領域まで押す（1 回の「掃き」）。穂を上げて次の掃きを選び、これを繰り返す。アームで掃く動作（穂を振る）は使わない。
- **根拠**（2026-10-30、sim で確認）: 穂を 45° または 60° に傾けて床に押し当て、台車を 0.15m/s で 0.6m 進めると、2 列に並べたゴミ 10 個が、横にずれず、乗り上げもせず、穂先の 2〜5cm 前にまとまって進んだ。
- **入力**: `SweepState`（ゴミの位置、目標領域の位置、台車の位置と向き、アームの関節位置）だけ。シーンに依存しない（Loft では、障害物の回避を足す。P7）。`read_state(env)` が sim の真値から作る。
- **出力**: sim の action（9 次元。台車の速度はワールド座標系）。評価では、学習したポリシーと同じく contract の LeRobot 形式に直してから env に渡す。

### アームの姿勢

- 穂先を台車の中心から 0.50m 前に置き、穂の長さの向きを床から 45° 傾け、穂の幅の向きを台車の左右にそろえる。前に押してもゴミが横に逃げない。
- 関節位置は、起動時に数値 IK で求める（`calibrate_arm`）。関節の状態を書き換えて順運動学を調べるので、エピソードの外で行う。条件は 5 つ（穂先の前後の位置と高さ、穂の幅の向き 2 つ、傾き）で、関節も 5 つ。
- 穂の高さは 4 段階（-0.01、0.02、0.05、0.08m）。-0.01m は床より 1cm 下を狙い、アームの柔らかさで穂を押し付ける（実際の穂先の中心は床から約 9mm。穂の厚みの角が床に当たる）。上げ下げは、この間を 0.5 秒で補間する。
- 移動の間は、既定の姿勢（関節がすべて 0。穂は front カメラの画面の上の端にあり、床を隠さない）にする（2026-10-31 から。それまでは穂を 0.08m に上げた姿勢のまま移動し、穂が front カメラの画面の中央をふさいでいた）。穂を上げた姿勢との間は 1 秒で補間する。穂を上げた後は台車を動かしながら移動の姿勢へ移し、開始位置の 0.15m 手前から穂を上げた姿勢へ戻す。
- 穂先は、台車の中心線から右に 0.145m ずれる。肩の位置と箒の握りの向きによるもので、穂の幅の向きを左右にそろえたまま中心線の上に置く解はない（傾き 30〜90°、前方 0.35〜0.55m で調べた）。計画器は、このずれを台車の位置で補う。
- 届く範囲: 穂を床に当てられるのは、傾き 45° なら前方 0.45〜0.55m、60° なら 0.35m 付近。

### 掃きの選び方（`choose_pass`）

- 押し終わっていないゴミ（目標領域の縁から 2cm 以上内側にないもの）それぞれについて、そのゴミから目標領域の中心への向きを、掃く向きの候補にする。横のずれ（-6〜+6cm）と組み合わせる。
- 候補ごとに、次を数える。
  - 穂の中心から 8.5cm 以内のゴミは、まっすぐ押される。そのうち、目標領域の中心線から 12cm 以内のものが、目標領域に入る見込み。
  - 台車がゴミを轢くか。掃く間の台車の通り道（穂の左側）に、まっすぐ押されないゴミがあれば轢く。穂の端をかすめるだけのゴミ（穂の中心から 8.5〜11.5cm）は押されずに残るので、轢く側に数える。
- 轢かない候補のうち、入る見込みのゴミが最も多く、掃く距離が最も短いものを選ぶ。
- 穂は、最も手前のゴミの 5cm 手前で下ろし、目標領域の中心の 3cm 手前で止める（ゴミは穂先の前にたまるので、中心付近に集まる）。

### 台車の動き

- **押した後**（2026-11-01 から。[sweep_experiments.md](sweep_experiments.md) の実験 10）: 穂を上げ、掃いた跡に沿って下がりながら、押し終わっていないゴミの重心の方へ向きを変える。掃いた跡はゴミを押し出した直後で空いているので、後ろが見えなくても当たらない。押した後にこぼれたゴミは台車の横や後ろにあり、下がりながら向きを変えることで front カメラに入れる。下がる距離は 0.15〜0.6m で、ゴミの重心から、次の開始位置の手前の点と同じだけ離れるまで（次の回り込みで外へ出る、つまり後ろ向きに進むことがないように）。
- **開始位置へ**（2026-10-31 から重心を向く。実験 6。2026-11-01 から回り込み。実験 10）: 押し終わっていないゴミの重心を向いたまま、重心のまわりを、半径を保つか縮めながら回り込む（`orbit_route`。15° ごとの経由点。台車から見て横か前へ進む）。開始位置の 0.15m 手前の点まで来たら、そこから前へ進んで入る（開始位置の 0.4m 手前から 0.15m 手前の間で、掃く向きへ向きを切り替える）。回り込む道がゴミから 0.21m（台車の半径 0.165m + ゴミの半分 + 3cm）以内を通るときは、ゴミを囲む円（開始位置の手前の点より外側）の上の点を経由する最短の経路にする（`plan_route`）。開始位置の候補を選ぶとき（`choose_pass`）は、手前の 0.15m の区間も台車がゴミに当たらないかを調べる。
- 後退するのは、押した後に掃いた跡を戻るときだけにする（移動中の後退は 25% から 9% に減った。実験 10）。学習したポリシーは、見えない後ろのゴミへ下がって当たることがあった（実験 8）。後退をすべてやめて前進だけで回り込むと、ゴミが長く画角から外れ、学習したポリシーは大きく悪化した（実験 9）。
- 目標領域がロボットとゴミの間にある配置では回り込みに時間がかかるので、制限時間は 40 秒にしている。
- 速さは、移動 0.3m/s、押す 0.2m/s、回転 90°/s 以下（上流のテレオペの最大と同じ）。加速度も 0.8m/s²、4rad/s² 以下に抑える（学習データの動きを滑らかにする）。
- 押す間は、穂先が掃く線から外れないように横の速度で補い、向きを保つ。

## 評価（`tools/sweep_eval.py`、`make sweep-eval`）

- `make sweep-eval EVAL_ROUNDS=30` で、計画器に 30 ラウンド解かせる。結果は `data/sweep/eval/<日時>/` の `rounds.jsonl`（ラウンドごと）と `summary.json`（成功率と 95% 信頼区間（Wilson）など）に残す。
- ポリシーのインタフェースは `reset()` と `act(obs) → [T, 9]`（contract の LeRobot 形式の action）。T 個の action を、それぞれ 2 step（30fps）ずつ続ける。バックエンドは `planner`（計画器）と `remote`（学習したポリシーの推論サーバ。下の「学習したポリシーの評価」）。
- 成功は終了条件 `success`（8 個以上）。40 秒で時間切れ（2026-11-01 から。それまでは上流の既定の 25 秒。計画器を後退しない動きにしたため。[sweep_experiments.md](sweep_experiments.md) の実験 9）。`EVAL_TIME_LIMIT` で評価だけ変えられる（25 秒の条件と比べるときに使う）。datagen と dagger はタスクの既定に従う。
- ラウンドごとの指標: 成功、目標領域に入った個数、かかった時間、`base_min_dist`（台車の中心から最も近いゴミまでの距離の最小値。0.165m 未満なら、ゴミに当たったか、台車の下にくぐらせた）、`view_fraction`（押し終わっていないゴミのどれかが front カメラの水平の画角 ±26.8° に入っていたフレームの割合。上下の画角と、穂に隠れるかは見ない）。

### 状態の記録（`tools/leisaac_ext/sweep_log.py`、2026-11-01 から）

評価（datagen、dagger も同じ）は、動画とは別に、後から状態を調べたり再生したりできる記録を常に残す。30 ラウンドで 2MB 弱（1 ラウンド約 55KB）。

## 自動生成（`make datagen`）

`make datagen DATASET=sweep_floor NUM=50` を実行すると、計画器が解いたエピソードのうち、成功したものだけを `data/datasets/sweep_floor.hdf5` に記録します（`sweep_eval.py --record`）。

- 終わる条件: 成功が `NUM` 個集まるか、ラウンドが `2 × NUM + 10` 回に達したとき。
- 同じ名前のファイルが既にあれば止めます。上書きも追記もしません。
- 一緒に残るもの:
  - `sweep_floor.sim.env`: 記録したときの `SIM_DEVICE` と `TEX_BUDGET`。`sweep-replay` で照合します（teleop と同じ仕組み）。
  - `sweep_floor.datagen/rounds.jsonl`: ラウンドごとの結果。記録したラウンドには、HDF5 の中の番号（`episode`。`demo_<番号>`）が付きます。
  - `sweep_floor.datagen/summary.json`: シード、成功率、ファイルの大きさなど。同じシードで実行し直せば、同じデータができます（CPU 物理）。
- 記録の仕組み:
  - isaaclab の RecorderManager を、成功したものだけを書き出すモード（`EXPORT_SUCCEEDED_ONLY`）で使います。
  - 上流の teleop が使う StreamingRecorderManager は、すべてを書き出すモードにしか対応していないので使いません。
  - エピソードは、終わるまでメモリにためておき、終わったときに gzip で圧縮して書き出します。
- ラウンドの間に `env.reset()` は呼びません。前のラウンドの終わりの自動リセットが返す観測から、次のラウンドを始めます。
  - isaaclab は、リセットの後も終了条件 `success` の値を残します。
  - そのため、自動リセットの直後に `env.reset()` を重ねると、初期状態だけのエピソードが「成功」として書き出されてしまいます。

### HDF5 の中身

上流の teleop で記録したデータと同じ形式です。エピソードは `data/demo_<番号>` に入っています。T は step の数で、記録は 60Hz です。計画器は同じ action を 2 step 続けます。

| キー | 形 | 内容 |
|---|---|---|
| `actions` | [T, 9] | env に渡した sim の action（`lekiwi-leader` の構成。台車の速度はワールド座標系） |
| `obs/front`、`obs/wrist` | [T, 240, 320, 3] uint8 | step の前の画像 |
| `obs/joint_pos`、`obs/joint_vel` ほか | [T, 9] など | step の前の観測（関節は `SIM_JOINT_NAMES` の並び） |
| `states/...` | [T, ...] | step の後の状態（ロボットの関節、ゴミと目標領域の位置と速度。env の原点からの値） |
| `initial_state/...` | [1, ...] | リセットした直後の状態（replay の始まり） |
| 属性 `success`、`num_samples` | — | 成功の印（常に True）と、step の数 |

- 学習データへの変換（P5、後述の「変換」）では、`contract.frame_indices` で 1 step おきに取り出し（30fps）、`contract.to_lerobot` で LeRobot 形式にします。
- エピソードの属性 `seed` は書き出されません（isaaclab の RecorderManager は書き出さず、上流の StreamingRecorderManager だけが書き出す）。シードは `summary.json` にあります。

### 確認のしかた

記録を確かめるには、次の 2 つの方法があります。

**1. 中身を見る（`make sweep-inspect DATASET=sweep_floor`）**

Kit を起動せずに HDF5 を読みます。出力先は `data/sweep/inspect/sweep_floor/` です。

- 端末に、エピソードごとの一覧を出します。
  - 項目は、step の数、時間、成功の印、目標領域に入ったゴミの個数（最初 → 最後）、自動生成のときのラウンドの番号、掃きの回数、`base_min_dist` です。
  - 成功していないエピソードや、画像の形が違うエピソードがあれば `[NG]` を出します。
  - 最後の行は `SWEEP INSPECT <問題のないエピソードの数>/<全体> ok` です。
- `overview.png`: 全エピソードを上から見た図を、10 列に並べた画像です。
  - 青は目標領域です。
  - 灰色の点は、ゴミの最初の位置です。
  - 緑と赤の四角は、ゴミの最後の位置です（緑は目標領域の中、赤は外）。
  - 黄色の線は台車の通り道で、円は台車の外形と向きです。
  - 一目で、全エピソードが目標領域に寄せ集めて終わっているかを確かめられます。
- `episode_<番号>.mp4`: front、wrist、上から見た図を横に並べた動画です。
  - 30fps の実時間で、学習データと同じフレームを使います。
  - `EPISODES="0 7"` で、動画にするエピソードを選べます（省略するとすべて）。
  - 上から見た図には、その時点の目標領域の中のゴミの個数（`in=`）を出します。

**2. 再生する（`make sweep-replay DATASET=sweep_floor EPISODES="0 7"`）**

記録した初期状態に戻して、記録した action を流します。流し終えたときに、成功するか（8 個以上）と、ゴミの最終位置の記録とのずれを調べます。

- 最後の行は `SWEEP REPLAY <成功したエピソードの数>/<全体> succeeded` です。
- 結果は `data/sweep/replay/<日時>/replay.jsonl` に残ります。
- `HEADLESS=0` にすると、GUI に実時間で表示します。
- ゴミの色、照明、カメラの位置のランダム化は状態に含まれないので、再生の見た目は記録と違います。物理には影響しません。記録の画像は `sweep-inspect` の動画で見てください。
- 上流の `make replay` は、成功したかどうかを確かめないので、このタスクには使いません。

## 変換（`make convert`）

`make convert DATASET=sweep_floor` で、`data/datasets/sweep_floor.hdf5` を LeRobot 形式に変換し、`data/lerobot/sweep_floor/` に出力します。本体は `tools/sweep_convert.py` です。

- train のイメージ（`docker/envs/train`。lerobot 0.4.2、h5py、torch 2.7.0 の cu128）で動かします。Kit も GPU も使いません。
  - sim の環境に lerobot は入れません。isaacsim が固定している numpy 1.26.0 などと衝突するおそれがあり、sim の環境を変えないためです。
- 出力先が既にあれば止まります（上書きも追記もしません）。作り直すときは、別の `DATASET` 名で変換するか、`data/lerobot/<名前>/` を消してから実行してください。

### 中身

| 項目 | 内容 |
|---|---|
| 形式 | LeRobot v3.0（lerobot 0.4.2 の `LeRobotDataset`）。`repo_id` は `local/<DATASET>`、`robot_type` は `lekiwi_client`（実機の LeKiwi を lerobot で記録したときと同じ） |
| フレーム | 30fps。60Hz の記録から 1 step おきに取り出す（`contract.frame_indices`） |
| `observation.state` / `action` | 9 次元の float32。キー名と単位は contract（モータの正規化値と、ロボット基準の台車の速度。`theta.vel` は deg/s） |
| `observation.images.front` / `.wrist` | 320×240 の動画。lerobot の既定の AV1（libsvtav1、crf 30、GOP 2） |
| 指示文 | `contract.INSTRUCTION`（全フレームで同じ） |
| `convert.json` | 変換元、フレームの数、かかった時間、照合の結果（lerobot は読まない） |

読み込むときは、train のイメージで `LeRobotDataset("local/sweep_floor", root="/workspace/data/lerobot/sweep_floor")` とします。

### 照合

変換した後、`LeRobotDataset` で読み直して、すべてのフレームを HDF5 と比べます。最後の行が `SWEEP CONVERT PASS` なら合格です。

- state と action は、ビット単位で一致すること。
- 画像は、動画の圧縮による差（画素の値 0〜255 の平均絶対誤差）が 4 以下であること。
- フレームがずれていないこと。
  - 隣り合うフレームの差（中央値 0.4 程度）は圧縮の差（1.3 程度）より小さいので、誤差の上限だけでは 1 フレームのずれを見分けられません。
  - そこで、エピソードごとに、同じ番号のフレームとの差が、前後に 1 フレームずらしたときの差より小さいことを確かめます。

`make check` の 6 番目（`tools/train_check.py`）では、ユーザーのデータを使わずに、次の 2 つを確かめます。

- contract のキー名とカメラの名前が、lerobot 0.4.2 の実機の LeKiwi（`LeKiwiClient`）と一致すること。そのために、train には `lerobot[lekiwi]`（feetech-servo-sdk と pyzmq）を入れています。
- 合成した小さな記録（2 エピソード、動く四角の画像）を変換して、照合が通ること。

### 結果（2026-10-30）

| 項目 | 結果 |
|---|---|
| 変換（`make convert DATASET=sweep_floor`） | 50 エピソード、21,676 フレーム。`SWEEP CONVERT PASS` |
| 時間 | 5.4 分（変換 2.5 分、照合 2.9 分） |
| 大きさ | 41MB（HDF5 の 1.74GB の約 1/40） |
| 画像の平均絶対誤差 | front は平均 1.33、最大 2.51。wrist は平均 1.65、最大 2.53 |
| フレームのずれの検出 | 前後に 1 フレームずらすと、差は 0.1〜0.4 大きくなる（全エピソードで、ずれなし） |

- GR00T N1.5 は、lerobot 版（`lerobot.policies.groot`）を使うので、v3.0 のまま学習できます（Isaac-GR00T 版が読むのは v2.1 形式。P6f で lerobot 版が使えないと分かったときに、v2.1 での出力を考えます）。

### 中身（`tools/sweep_train.py`）

- lerobot 0.4.2 の `lerobot-train` を呼ぶ薄いラッパーです。Docker の外（Colab）でも、train の環境（`docker/envs/train` の lock）があれば同じように動きます。
- ポリシーごとの既定（`PRESETS`）に、共通の設定（ローカルのデータセット、Hub に上げない、wandb を使わない、チェックポイントは steps の 1/5 ごと）を足して実行します。`-- ` の後ろは、そのまま lerobot-train に渡します。
- 出力先は `data/train/<TRAIN_NAME>/`（lerobot の output_dir。`checkpoints/<step>/pretrained_model/` と `checkpoints/last`）。既にあれば止めます（上書きも再開もしない）。実行したコマンドと結果は `sweep_train.json` に残ります。`data/policies/` は make assets で取得するポリシーの場所なので、学習の出力は分けています。

| ポリシー | 始め方 | 既定の steps / batch | 注意 |
|---|---|---|---|
| act | 新しく作る（`--policy.type=act`。backbone は ImageNet の ResNet18） | 100,000 / 8 | — |
| smolvla | `lerobot/smolvla_base` から | 20,000 / 64 | 下の「事前学習済みのモデルの入出力」 |
| groot | `nvidia/GR00T-N1.5-3B` から（`--policy.type=groot`。LLM と視覚エンコーダは凍結） | 20,000 / 32 | flash-attn が必須。ローカルでは学習できない |

- **事前学習済みのモデルの入出力**: smolvla_base は、入出力の名前と形（camera1〜3、state と action が 6 次元）を自分の設定に持っていて、lerobot はそれをデータセットに合わせません。action が 6 次元のままだと、推論で台車の速度（7〜9 番目）が切り捨てられます。そこで、`sweep_train.py` がデータセットの `meta/info.json` から入出力の形を作り、`--policy.input_features` / `--policy.output_features` で上書きします。カメラは rename_map で front → camera1、wrist → camera2 にします。dict の上書きは足し込みなので、camera3 は設定に残りますが、画像がないカメラは飛ばされます（`empty_cameras=0`）。
- **flash-attn**: lerobot の groot が必須にしています（視覚エンコーダが flash_attention_2 を固定で使う）。ソースからのビルドを避け、公式の配布物（2.8.3、torch 2.7、CUDA 12、C++11 ABI、Python 3.11 向け）を URL で固定しています。この GPU（RTX 5070、sm_120）でも動きます（`make check` の 6 番目で確かめる）。
- 取得したモデルの重み（Hub と torchvision）は `data/.cache/` に置きます（GR00T とあわせて約 8GB）。

### 確認（`make check` の 6 番目）

変換の確認（上の「照合」）に加えて、学習するポリシー（ACT、SmolVLA、GR00T）を import できること、flash-attn がこの GPU で動くこと、合成データで ACT を 4 step 学習してチェックポイントが残ることを確かめます。

### SmolVLA をローカルで学習できるか（2026-10-30、P6d の後）

`make train DATASET=sweep_floor TRAIN_POLICY=smolvla TRAIN_STEPS=200 TRAIN_BATCH=<32|16>` で測りました（VRAM は nvidia-smi で 2 秒ごと、画面の分 1.2GB を含む全体の値）。

| batch | 1 step | VRAM のピーク | 既定の 20,000 step の見込み |
|---|---|---|---|
| 32 | 0.595 秒 | 9.5GB | 約 3.3 時間 |
| 16 | 0.297 秒 | 6.1GB | 約 1.7 時間 |

- batch 32 まではローカルで学習できます。既定の batch 64 は、この伸び方（batch 16 ごとに約 3.4GB）だと 12GB に収まりません。lerobot 0.4.2 の学習には勾配の累積がないので、batch を下げると 1 回の更新のサンプルが減ります。既定と同じサンプル数（20,000 × 64）を batch 32 で見るなら 40,000 step（約 6.6 時間）です。
- チェックポイントは 1 つ約 1.2GB です（200 step で 5 つ、6.2GB）。
- 学習率のスケジュールは steps に合わせて縮むので、step を変えても最後まで下がります。

## 学習したポリシーの評価（`tools/policy_server.py`、`make sweep-eval EVAL_POLICY=remote`）

```bash
make sweep-eval EVAL_POLICY=remote TRAIN_NAME=sweep_floor-act EVAL_ROUNDS=30   # 推論サーバを起動 (make policy-up) してから評価する
make sweep-eval EVAL_POLICY=remote TRAIN_NAME=sweep_floor-act TRAIN_CHECKPOINT=020000   # 途中のチェックポイント
make sweep-eval EVAL_POLICY=remote TRAIN_NAME=sweep_floor-act EVAL_SEED=1793361616      # シードを固定する (ラウンドごとの配置がそろう)

make policy-down                                                                 # 推論サーバを止める (make down でも止まる)
```

- 推論サーバ（compose の `policy`、profile `inference`）は train のイメージで動き、`data/train/<TRAIN_NAME>/checkpoints/<TRAIN_CHECKPOINT>/pretrained_model` を読みます。TRAIN_NAME か TRAIN_CHECKPOINT を変えて `make policy-up` すると、作り直されます。GR00T の推論サーバ（:5555）とは別のポート（:5556）なので、同時に起動できます。
- ポリシーと一緒に、学習のときに保存された前処理と後処理（正規化、SmolVLA のカメラ名の読み替えと言語のトークン化）を読むので、学習と同じ変換になります。GR00T（lerobot 版）は、読み込むときにデータセットの統計を渡す必要があるので、P6f で扱います（いまはサーバが止める）。
- 通信は `tools/leisaac_ext/remote.py`（ZMQ の REQ/REP。JSON のヘッダと、numpy の配列の生のバイト列）。sim は観測を学習データと同じ形（`contract.to_lerobot` の state と、240×320 の uint8 の画像）で送り、`predict_action_chunk` の先頭 `ACTION_HORIZON` 個（既定 16、約 0.53 秒分）を受け取ります。応答が `POLICY_TIMEOUT_MS` 以内になければ止めます。
- `summary.json` には、サーバの情報（ポリシーの種類、チェックポイントの step、chunk の長さ、サーバの VRAM のピーク）と ACTION_HORIZON が残り、`rounds.jsonl` には推論の回数と平均の時間が残ります。
- `make check` の 6 番目で、合成データで学習した ACT のチェックポイントを推論サーバに読ませ、action の系列が返ることを確かめます。
- `EVAL_VIDEOS=1` で、ラウンドごとの動画 `videos/round_<番号>_<success|failure>.mp4`（front、wrist、上から見た図を横に並べた 30fps の実時間。`make sweep-inspect` の動画と同じ描き方で、`tools/leisaac_ext/sweep_video.py` を共有する）と、全ラウンドの終わりの図を並べた `overview.png`（S/F、時間、目標領域に入った個数）を残します。動画は 1 ラウンド 0.5〜1.5MB です。
- シードがそろえるのは配置で、推論や物理の細かな違いで、その後の動きは分かれることがあります（[sweep_experiments.md](sweep_experiments.md) の注意）。
- 実験の経緯と結果は [sweep_experiments.md](sweep_experiments.md) にまとめています。

### 結果（2026-10-30、計画器のデータを 200 エピソードに増やす）

```bash

make convert DATASET=sweep_floor200             # 85,841 フレーム、照合 PASS（image_mae の最大 2.6）、22 分、161MB
```

| 50 エピソード | 100,000 | 7/30（23%、12〜41%） | 4.2 | 24/30 | `....S.......S..S..S.S...S...S.` |
| 50 エピソード | 60,000 | 11/30（37%、22〜55%） | 4.4 | 20/30 | `S...SS.S...S...S.S.SS...S.S...` |
| 200 エピソード | 100,000 | **17/30（57%、39〜73%）** | 5.7 | 13/30 | `S.SSSS.SS..SS..S.S.S.S..SS.SS.` |

## DAgger（`make dagger`）

計画器のデータだけで学習したポリシーは、少しずれると計画器のデータにない状態（台車がゴミに近すぎるなど）に入り、立て直せないことがあります（[sweep_experiments.md](sweep_experiments.md)）。DAgger は、学習したポリシーで動かし、ポリシーが行った先の状態で計画器が出す action を正解として記録し、元のデータに足して学習し直す方法です。計画器は sim の真値を読むので、どの状態からでも正解を出せます。

```bash
make dagger DATASET=sweep_dagger1 TRAIN_NAME=sweep_floor200-act NUM=50     # 50 ラウンド。推論サーバを起動してから動かす
make convert DATASET=sweep_floor200_dagger1 CONVERT_FROM="sweep_floor200 sweep_dagger1"
make train DATASET=sweep_floor200_dagger1
make sweep-eval EVAL_POLICY=remote TRAIN_NAME=sweep_floor200_dagger1-act EVAL_ROUNDS=30 EVAL_SEED=1793361616
```

- 中身は `sweep_eval.py --policy remote --record --dagger`。学習したポリシーの action で動かし（chunk ごとに確率 `DAGGER_BETA` で計画器の action で動かす。既定 0）、各フレームで計画器が出した action を `actions` に、実際に動かした action を `executed_actions` に記録します（isaaclab の記録の項目を差し替える。形式は datagen と同じ）。成功も失敗も、すべてのラウンドを記録します。
- 計画器は、台車の速度の指令を「自分の前の指令」から加速度の上限をかけて作ります。ポリシーが動かした後では前の指令と実際の速度が違うので、DAgger では毎フレーム、前の指令を実際の台車の速度に合わせ直してから正解を求めます。計画器の状態（どの掃きの途中か）はそのまま進み、押し終わっていないゴミがあれば計画し直します。
- `make convert` は `CONVERT_FROM` に並べた記録を順につなぎます。datagen の記録は成功したエピソードだけのはずなので、失敗があれば止めますが、DAgger のエピソード（`executed_actions` がある）は失敗したものも使います。`make sweep-replay` は DAgger の記録を `executed_actions` で再生し、`make sweep-inspect` は失敗したラウンドを問題として数えません。
- `make check` の 6 番目で、datagen と DAgger の合成データをつないで変換できることを確かめます。

### Loft でのデータの取り直し（P7、2026-10-30 に決定）

床のシーンで P3〜P6 の流れ（計画器、自動生成、変換、学習、評価）がすべて通ることを確かめてから、Loft（上流の CleanupTrash の部屋）でデータを取り直して学習し直す。床だけでは背景が単調で、実際の部屋の見た目に弱くなるおそれがあるため。

- そのまま使うもの: contract.py、変換器、sweep_eval.py（評価と自動生成）、箒付きのロボット、ゴミ、目標領域、成功の判定、ランダム化の部品、学習の手順。
- 作り直すもの:
  - シーンとロボットの位置（CleanupTrash は (-2.3, 0.8)）。
  - 配置の範囲（家具と重ならない範囲を決める）。
  - 計画器の障害物の扱い（家具の脚や壁を避ける）。
  - 照明（Loft の照明を使い、床のシーン用の強さの変更は使わない）。
- コスト: Loft は約 20 steps/s（床の約 4 分の 1）で、VRAM は約 5.3GB。自動生成の時間は床の約 4 倍になる見込み。
- そのための P3 の方針: 計画器は、ゴミの位置、目標の位置、ロボットの姿勢だけを入力にした、シーンに依存しない関数で作る。障害物の回避は P7 で足す（P3 では作らない）。

## 未確定の事項

- 最初の画像では、ゴミは 5〜10 ピクセル、目標領域は細い帯でしか見えない。学習したポリシーが見分けられるかは、P6 で確かめる（計画器は真値を使うので影響しない）。
- 質量と摩擦のランダム化を使うなら、その値を記録して replay で戻す仕組みが要る（P7 で検討する）。
- 計画器のデモでは、アームは決まった姿勢の間を動くだけで、掃く動きは台車が担う。学習したポリシーも主に台車の動きを学ぶことになる。アームで掃く動作が必要になったら、計画器に足す。
- sim では、2cm のゴミが台車の下（床から約 2.8cm）をくぐる。実機の台車の地上高と合っているかは、実機に移す段階で確かめる。
- **将来の拡張（2026-11-01、今回は行わないとユーザーが決定）: 強化学習の併用**。Isaac Lab の並列環境（GPU 物理、カメラなし）で、sim の真値を入力にした教師を PPO などで学習し、その教師にデモを作らせ、DAgger の正解も付けさせて、画像で動く ACT に移す。報酬は、ゴミが目標領域へ近づくこと、入った数、台車がゴミに当たることへの罰、ゴミを front の画角に入れておくことへのご褒美で組む。教師は「今の状態 → 動き」だけで決まるので、計画器の内部の状態に依存して失敗した DAgger（[sweep_experiments.md](sweep_experiments.md) の実験 5、7）の問題が起きない。判断が要る点は、GPU 物理を全タスク共通の CPU 物理の例外にするか、強化学習のライブラリを sim の環境に足すこと。画像を入力にした強化学習は、VRAM 12GB では並列の数が少なく不安定なので採らない。Genesis などへの乗り換えは、アセット、シーン、記録、描画を作り直すことになり、描画も変わってこれまでの結果と比べられないので採らない。
